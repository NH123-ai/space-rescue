# 接入队友模块（从“测试桩数据”切到“正式数据”）

> 现状：队友 A（数据）/ B（算法）/ D（主程序）的代码还没写完，
> 所以公开站点先用**视觉模块测试台**（`viz_test` + `mock_data.c`）生成的数据跑。
> 这个页面上会显示 **“数据：测试桩（等队友模块接入）”**，一眼能看出还没接正式模块。
>
> 等队友交付后，**只需要换一条生成命令**，前端（HTML/CSS/JS）一行都不用改。

---

## 一、为什么可以无缝切换

两边产出的**数据格式完全一致**：

```
web/traces/catalog.js            ← 场景清单（key / title / desc / file）
web/traces/<key>/trace.js        ← 单场景数据（window.RESCUE_TRACE = {...}）
web/traces/<key>/trace.json
```

区别只在 `meta.dataSource` 字段：`"mock"` 还是 `"full"`，前端据此显示徽标。

| 谁生成 | 命令 | dataSource |
| --- | --- | --- |
| 测试台（现在用） | `viz_test.exe --emit-all web/traces` | `mock` |
| 正式程序（队友就绪后） | `space_rescue.exe --trace-all web/traces` | `full` |

## 二、切换步骤（3 步）

1. **确认正式程序能编过、测试全过**

   ```bat
   cd /d "D:\dshworkplace\C analyze\space_rescue"
   build.bat
   space_rescue.exe --test        :: 8 个用例应全 PASS
   ```

2. **重新生成站点数据**

   ```bat
   tools\build_site.bat           :: 自动：正式模块优先，编不过才退回测试台
   ```

   也可以强制指定：

   ```bat
   tools\build_site.bat full      :: 强制正式模块（编不过直接报错，便于发现队友代码问题）
   tools\build_site.bat mock      :: 强制测试台（演示/回归用）
   ```

3. **本地看一眼再发布**

   ```bat
   cd web
   python -m http.server 8777
   :: 打开 http://127.0.0.1:8777/index.html，确认右上角徽标变成“数据：正式模块”
   git add -A && git commit -m "接入队友 A/B/D 正式模块，站点切到真实数据" && git push
   ```

   GitHub Actions 也会自动做同样的判断（正式模块编得过就用正式数据），
   所以其实**只要把队友代码 push 上去，站点下次部署就自动切过去了**。

## 三、接进来之后要核对的 6 项

| # | 检查点 | 怎么看 |
| --- | --- | --- |
| 1 | 结构体字段没被改坏 | `space_rescue.h` 里 `Target`/`RescueData`/`RoutePlan` 只允许**末尾追加**，旧字段名一个都不能少 |
| 2 | 四个模块能一起编过 | `build.bat` 输出“编译成功”，0 error |
| 3 | 算法给出 4 条方案 | 界面“算法对比”面板有 4 张卡片，名字是 NN / EDF / 2-opt / 回溯 |
| 4 | 数据契约正确 | `python tools\selfcheck.py`，看“数据契约：不一致 0 个” |
| 5 | 牺牲状态能出现 | 打开 `?trace=tight`，切到“反向/交替基线”，目标变红叉、序列里划线 |
| 6 | 徽标与来源一致 | 右上角显示“数据：正式模块”，任务简报里“数据来源”写着 `traces/<key>/trace.js` |

> 若第 3 项只看到 2 条方案，说明 `main.c` 的 `run_all_plans()` 里少调了某个 `plan_*`；
> 若第 4 项不一致，通常是 `leg_t/leg_d` 与实际仿真不同步（可对比 `plan_simulate`）。

## 四、队友各自要交付什么（对照表）

| 组员 | 文件 | 必须提供的接口 | 说明 |
| --- | --- | --- | --- |
| A 数据 | `data_module.c` | `calc_3d_distance` / `update_target_pos` / `target_pos_at`；推荐还提供 `gen_scenario` | 视觉模块只用前三个；`gen_scenario` 用于批量生成站点场景 |
| B 算法 | `algorithm_module.c` | `plan_nearest` / `plan_urgency` / `plan_2opt` / `plan_backtrack` / `plan_simulate` / `plan_apply` / `plan_name` | 每条方案填一个 `RoutePlan`（顺序 + 每段时刻/距离 + 节点数 + 耗时） |
| D 主程序 | `main.c` | `run_all_plans` 收集 4 条方案，调用 `viz_write_trace`（或 `--trace-all`） | 站点数据由它驱动；`--trace-all` 的场景表可自己加 |
| C 视觉 | `viz_module.c`（已完成） | `viz_write_trace` / `viz_render_report` / `viz_console_sim` / `viz_draw_ascii_map` | 不需要队友改任何东西 |

**接口契约的唯一硬约束**：`RoutePlan` 里每段的 `leg_t[i]`（到达时刻）与 `leg_d[i]`（航段距离）
必须与 `plan_simulate()` 的仿真一致——前端会按“目标等速漂移 + 飞船分段匀速”反推，
不一致就会看到航线与目标错位（`tools/selfcheck.py` 会报“数据契约不一致”）。

## 五、常见问题

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| `tools\build_site.bat` 打印“正式模块还编不过” | 队友代码有 error / 缺文件 | 按报错补代码；暂时继续用测试桩数据不影响演示 |
| 站点徽标还是“测试桩” | 生成数据用的还是 `viz_test --emit-all` | 跑 `tools\build_site.bat full`，或直接 `space_rescue.exe --trace-all web/traces` |
| 页面数据没变 | 浏览器缓存 / 忘了重新生成 | `Ctrl+F5`；确认 `web\traces\catalog.js` 的时间戳是新的 |
| 想再加场景 | `main.c` 的 `g_site_scenes[]`（正式）或 `viz_test.c` 的 `g_mock_scenes[]`（测试桩）各加一行 | 重新跑 `build_site.bat` 即可，前端下拉框自动出现新场景 |
