# 队员 C 可视化模块升级说明

> 面向对象：小组成员 / 指导老师 / 答辩现场
> 对应大纲：**综合程序设计五 · 太空救援问题**，扩展功能 30 分中的“**界面及动画设计**、
> **设置目标初始状态并模拟演示救援过程**、**给出最佳救援方法**、**不同方法对比分析与效率评价**”

---

## 一、原方案哪里“简陋”

原分工里组员 C 只有三个函数（见原飞书文档接口）：

```c
void draw_console_sim(RescueData *rd);
void init_easyx_window();  void draw_3d_projection(...);  void run_rescue_animation(...);
```

实际问题：

| 问题 | 具体表现 | 对评分的影响 |
| --- | --- | --- |
| 信息密度低 | 控制台只能一行行打印“T+8.67 → 追踪 T8”，看不出空间关系 | 演示效果差，“可演示”只能靠口头描述 |
| 没有交互 | 不能暂停、回看、跳到某个目标，也无法让老师指定“看第 5 个目标” | 现场答疑被动 |
| 依赖环境 | EasyX 需要额外安装、需要打开 IDE 编译，机房/同学电脑经常装不上 | 演示风险高 |
| 数据与画面耦合 | 画图函数自己算位置，改动算法要连带动画代码 | 模块一致性差 |
| 算法对比看不到 | 四种策略的航程/节点/耗时只能靠表格念 | 扩展功能“效率评价”拿不到分 |
| 关键状态缺失 | 牺牲目标、剩余生存时间、坐标刷新这些题目核心要素表现不出来 | 与题意脱节 |

## 二、升级目标与设计约束

**目标**

1. 同一份 C 数据，能同时撑起 **控制台演示**、**EasyX 演示**、**网页 3D 演示** 三种呈现；
2. 网页端要能**拖时间轴、切方案、看指标**，让“演示”变成可视化实验，而不是放录像；
3. 零第三方依赖、断网可跑、双击即开（机房笔记本也能演示）；
4. 不改动组员 A/B/D 的函数签名，接口演进只做**追加**。

**约束（来自大纲）**

- 必须仍是 C 语言实现，核心算法由 C 完成（网页只做渲染，不做计算）；
- 大纲核心知识点提到 “界面设计，EasyX，或 QT 或 VS 的对话框设计”，因此 **EasyX 路径保留**；
- MAX_TARGET_NUM = 12，回溯规模受限，界面要能表达“牺牲”而非只展示成功。

## 三、升级后的架构：算与画分离

```
            ┌───────────────────────────────────────────────────────────┐
            │                      A 数据模块 (data_module.c)            │
            │  场景生成 / 文件读取 / 漂移模型 p(t)=p0+v·t / 三维距离      │
            └───────────────┬───────────────────────────────┬───────────┘
                            │ RescueData*                   │
                            ▼                               ▼
      ┌─────────────────────────────────┐   ┌─────────────────────────────────┐
      │  B 算法模块 (algorithm_module)   │   │  C 可视化模块 (viz_module.c)     │
      │  NN / EDF / 2-opt / 回溯+剪枝    │   │  ① 控制台仪表盘（ANSI）           │
      │  拦截时间解析解 + 仿真            │   │  ② ASCII 俯视图                  │
      │  → RoutePlan（含节点数/耗时）     │   │  ③ trace 导出（JSON / JS）  ★    │
      └────────────────┬────────────────┘   │  ④ EasyX 动画（可选编译）         │
                       │ RoutePlan[]          └───────────────┬─────────────────┘
                       ▼                                     │ web/trace.js
            ┌─────────────────────────┐                      ▼
            │  D 主程序 (main.c)       │        ┌───────────────────────────────┐
            │  命令行 / 测试用例 / 联调 │        │ 浏览器渲染层（web/，纯前端）    │
            └─────────────────────────┘        │  3D 场景 + HUD + 时间轴 + 图表 │
                                               └───────────────────────────────┘
```

**关键决策**

- C 端**不逐帧导出坐标**，只导出“目标初值 + 速度 + 各航段时刻”。
  因为题目本身给了两条解析规律（目标等速漂移、飞船分段匀速），
  浏览器用 9 个目标的 6 KB 数据就能还原任意时刻画面，
  于是时间轴可以任意拖拽/倍速/回放——这是“录像式动画”做不到的。
- 网页端加载 `trace.js`（`window.RESCUE_TRACE = {...}`）而不是 `fetch('trace.json')`，
  因为双击打开时是 `file://` 协议，浏览器禁止 fetch 本地 JSON；用 `<script>` 规避 CORS。
- 控制台版本保留并升级（ANSI 彩色 + 甘特图 + 压力条），
  在没有图形环境、或需要把输出贴进实验报告时仍然可用。

## 四、可视化模块接口 v2（只追加，不改旧签名）

```c
/* ---- v1 保留 ---- */
void draw_console_sim(RescueData *rd);                       /* 升级为时钟推进式演示 */

/* ---- v2 新增 ---- */
void viz_render_report(const RescueData *rd,                 /* 控制台仪表盘          */
                       const RoutePlan *plans, int n_plans,
                       const char *plan_titles[]);
int  viz_write_trace(const RescueData *rd,                   /* 导出 web/trace.{json,js} */
                     const RoutePlan *plans, int n_plans,
                     const char *out_dir);
void viz_draw_ascii_map(const RescueData *rd);               /* ASCII 俯视图          */
const char *scenario_name(int sc);                           /* 场景名                */
int  viz_choose_best(const RoutePlan *plans, int n_plans);    /* 推荐方案：获救→航程→耗时 */
void viz_set_color(int enable);                              /* 关 ANSI 颜色          */
int  viz_width(const char *s);                               /* 中文占 2 列的宽度      */
void viz_pad_r / viz_pad_l(...);                              /* 按显示宽度对齐         */

/* ---- EasyX 可选（#ifdef EASYX，见 viz_easyx_optional.c）---- */
void init_easyx_window(void);
void draw_3d_projection(RescueData *rd, double now_time);
void run_rescue_animation(RescueData *rd);
```

### 共享结构体的 v2 变更登记（追加字段，向后兼容）

| 结构体 | 追加字段 | 原因 |
| --- | --- | --- |
| `Target` | `vx, vy, vz` | 题目要求位置随时间漂移，v1 无处存放速度 |
| `Target` | `life_left` | 仿真中剩余生存时间，用于控制台压力条与状态判断 |
| `RescueData` | `total_distance, saved_count, dead_count, algo_used` | 结果汇总，供输出与 UI 直接读 |
| `RescueData` | `origin_x/y/z` | 救援基点从“写死原点”改为可配置 |
| `RescueData` | `seed, scenario` | 场景可复现，并在界面上显示“当前是什么场景” |
| 新增 `RoutePlan` | 见 `space_rescue.h` | 一条完整方案：顺序 + 每段时刻/距离 + 节点数 + 耗时 + 可行性 |

> 说明：v1 的字段名、顺序、函数签名全部未变，原有代码可原样编译；
> 组员 A/B/D 只需在需要的地方读取新增字段即可。

## 五、网页端技术实现

| 关注点 | 做法 | 为什么这样做 |
| --- | --- | --- |
| 3D 渲染 | Canvas 2D + 手写球坐标相机与透视投影（yaw/pitch/dist → `scale = V/(depth+d)`） | 不引入 three.js，离线可跑、体积为 0，答辩电脑不用装东西 |
| 绘制顺序 | 星云 → 星空 → 地面网格 → 航线 → 基站 → 目标（按深度远到近排序）→ 飞船 → 特效 → 文字标签 | 保证遮挡关系正确、避免标签被后画的对象压住 |
| 性能 | 光晕预渲染成离屏精灵缓存；HUD 列表按帧节流（约 6 帧一次）；DPR 上限 2 | 1080p 下稳定 60 FPS，笔记本核显也不卡 |
| 状态推导 | 由 `legs[].t0/t1` + `outcome[]` 推导任一时刻的目标状态（等待/在途/获救/牺牲）与飞船位置 | 单一数据源，拖时间轴不会出现“画面与数字不一致” |
| 视觉语义 | 青=正常、琥珀=紧迫/在途、翠=获救、红=牺牲；生存环按剩余比例收缩，<20% 呼吸闪烁 | 与“最长生存时间”这一题眼直接对应 |
| 交互 | 拖拽旋转 / 滚轮缩放 / 双击复位 / 空格播放 / ←→ 单步 / R 复位 / C 环绕；时间轴可拖拽、可点事件跳转 | 老师随时点名“看第 3 个目标那一秒” |
| 深链接 | `index.html?t=40&plan=3&brief=0` | 可直接把某一帧截图/发给组员，便于远程讨论与写入报告 |
| 导出 | 当前帧导出 PNG；`@media print` 隐藏 3D 画布保留信息面板 | 报告里既能有画面，也能有表格 |

### 视觉模块的独立测试台（`viz_test/`）

视觉模块不再只能“跑完整流程才能看效果”。`viz_test/` 是只链接 `viz_module.c` 的
测试工程：假数据由 `mock_data.c` 手工构造，一条命令跑 **96 条断言**。

| 能力 | 命令 | 用途 |
| --- | --- | --- |
| 回归测试 | `build_test.bat` → `viz_test.exe` | 9 组断言，失败即打印期望/实际，退出码可用于脚本 |
| 交互调试 | `viz_test.exe --demo` | 键 5/6 调目标数与种子，立刻重印仪表盘 / 俯视图 / 过程模拟 |
| 外观预览 | `viz_test.exe --emit out` → `preview.html` | 用**真实渲染器**预览手工构造的数据，改 UI 不用等算法 |
| 联调校验 | `build_test.bat full` | 额外链接真实的 `data_module.c` / `algorithm_module.c`，验证接口对接 |

覆盖点里有两组是“踩过坑才写的”：过程模拟**不得修改调用者的 `RescueData`**
（否则导出的 trace 坐标整体漂移、网页航线错位），以及 `-0.0`/`1e-12` 这类
数值在 JSON 里必须写成 `0.000`（否则前端解析出 `-0` 影响坐标比较）。
`preview.html` 由 `sync_preview.py` 从 `web/index.html` 自动生成，
保证调试所见即正式页面所见。

## 六、答辩演示脚本（约 3 分钟）

1. **开场（20 s）**：`space_rescue.exe --trace web` → 打开页面 → 任务简报，
   念一句“9 个目标在漂移，飞船 10 单位/时间，每 5 个时间单位刷新一次坐标”。
2. **过程（60 s）**：点“开始演示”，边走边讲：
   生存环在收缩 → 飞船航段变琥珀 → 对接时扩散环 + “已获救”。
   中途按空格暂停，拖时间轴回退到 18 s，“这里是第 2 个目标，剩余生存 209”。
3. **算法对比（60 s）**：切到“算法对比”页签，
   点 NN / EDF / 2-opt / 回溯，说明总航程 1746 → 955 的差距与搜索节点 45 → 62 284 的代价；
   指出 ★ 推荐方案的选取规则（获救数 → 航程 → 耗时）。
4. **极端场景（30 s）**：`--n 12 --scenario tight --seed 8` 重新生成并刷新，
   展示红色牺牲目标与序列里的划线项，说明“回溯能救 9 个，贪心只能救 8 个”。
5. **收尾（10 s）**：点“导出 PNG”存一张最终帧；补一句工程性说明
   （同一份 `RescueData` 同时驱动控制台 / EasyX / 网页三种渲染器）。

## 九、局限与后续优化

1. **回溯节点上限**：n=12 时偶尔触达 300 万节点（≈200 ms）后返回当前最优。
   可加“下界估价 + 最近邻上界”提高剪枝率，或改成迭代加深 / 分支定界。
2. **仅前向贪心**：EDF 在长航段场景明显劣于 NN，可尝试“NN 与 EDF 的加权评分”自适应选择。
3. **实时推送**：现在是“跑完再导出”。若要现场改参数即时刷新，可让 C 起一个极简 HTTP/SSE 服务
   （`space_rescue.exe --serve 8080`），浏览器订阅事件流；这也是华为云在线模式的延伸方向。
4. **渲染升级**：目标数或特效继续增加时，可把 Canvas 2D 投影换成 WebGL（仍是零依赖的自写 shader）。
5. **过程录制**：`MediaRecorder` 录 `canvas.captureStream()`，一键导出 WebM 小视频贴进答辩 PPT。
6. **多目标轨迹叠加**：目前展示“选定方案”的航线，可再加“同屏对比两种算法的航线差异”。
